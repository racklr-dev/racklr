# Effect Rows for Racklr: A Fully Revised Plan

**Status:** Revised draft for working-group review
**Scope:** Extending the UIR and pass pipeline with algebraic effect rows, targeting Python (FastAPI, Django), TypeScript, React, and htmx. Next.js is treated as one instance of the general web-framework pattern, not as the design center.

**As-built vs planned:** §3.4, §6, and the Phase-0 half of §9 describe what is implemented and running in `racklr/effects/`; §5, §7, §8, and §11–§12 describe later phases (annotation extraction, contract algebra, runtime enforcement). The P0.3 acceptance bar is the Phase-0 half: zero `unknown` leaves with provenance on every edge.

---

## 1. The Corrected Focus

Effects exist to make the **mutator interfacing** generated by web frameworks safe. In every target stack, there is a set of functions that change state or interact with the outside world:

- **FastAPI route handlers** — async functions decorated with `@app.get`, `@app.post`, etc.
- **Django views and form handlers** — functions that receive requests and mutate the database.
- **React event handlers** — `onClick`, `onSubmit`, `onChange` callbacks.
- **htmx-triggered endpoints** — server-side functions that respond to partial-page requests.
- **Client-side state setters** — `useState` setters, `useReducer` dispatchers.

These are the **mutators**. The contract problem is to ensure each mutator performs only the effects it is allowed to perform, within its budgets and scopes. Racklr's UIR currently captures the structure of these mutators — `uir-fn` for handlers, `uir-event` for event bindings, `uir-call` for invocations — but not their effect behavior. This plan adds that layer.

---

## 2. What Racklr Has Today

Racklr provides:

- ANTLR4 grammar-driven parsing to CST.
- CST → UIR lowering with 40+ node types across Tier 0 (computational) and Tier 1 (OOP/module).
- UIR → Python 3 and JavaScript emitters with working round-trips.
- A documented UIR schema covering Tier 0 nodes: `uir-fn`, `uir-call`, `uir-if`, `uir-try`, `uir-decorated`, etc.
- 1,129 passing tests.

Tier 2 (UI component trees) is described in the schema as "models declarative component trees" but is **not yet implemented** in the UIR schema doc. The roadmap lists React/JSX and Svelte as planned Tier 2 lowering and emit targets.

The relevant existing infrastructure for this plan is the `uir-fn`, `uir-call`, `uir-decorated`, and `uir-try` nodes, plus the `lower-python.rkt` and `lower-javascript.rkt` modules that already handle decorators, async functions, and class methods.

## 3. The Effect Row Model

An effect row is an ordered set of **effect entries** attached to a function or mutator node.

### 3.1 Entry structure

Each entry has:

| Field | Description | Example |
|---|---|---|
| `name` | Opaque symbol, never interpreted by racklr | `llm`, `db`, `network`, `cache` |
| `modality` | `may`, `must`, or `must-not` | `may` |
| `ops` | Typed operation symbols the entry covers (empty = whole domain); each op is receiver-qualified — `db<QuerySet>.read` — so the capability names the concrete class that performs it | `(db<QuerySet>.read)` |
| `budget` | Integer upper bound on invocations | `5` |
| `scope` | Information-flow or resource qualifier | `reads=search_index` |

`ops` is where "grounded in the concrete call chain" becomes a data property: an op is `domain<ReceiverClass>.verb` — the domain comes from the class's module, the receiver class from the call-chain dataflow, and the verb from the method name via a per-domain DATA verb table. A coarse entry (empty ops) means "any op in this domain" and dominates; it is never narrowed by a precise entry.

### 3.2 Semantics

These bullets are **contract** semantics — what a declared capability means when it is checked. **Inference** semantics are how a body's row is computed (§6): every detected effect starts as a `must` obligation at its call site, and the control-flow composition around it decides the final modality — a sequence keeps it `must`, a branch (`if`/`match`) keeps `must` only when every branch must, a loop body / comprehension / short-circuit operand weakens it to `may`, and a `try` body weakens it because an exception can skip later statements. A callee's `must` propagates through an unconditional call and is demoted through a conditional one. An unresolvable call is recorded `unknown` (a tracked obligation, §3.4) and stays `unknown` through every region; a body with no recorded entries is `pure` (the empty row).

- **Absence is prohibition.** On the contract side, an effect a declared row does not list is `must-not` by default.
- **`may` is permission, not obligation.** A function typed `<may llm>` may or may not call the LLM.
- **`must` is obligation.** A function typed `<must llm>` must perform at least one LLM operation on every execution path.
- **Budgets are upper bounds** on operation invocations. Statically resolvable where the call graph is finite; otherwise lowered to runtime counters.
- **Scope is a constraint** on resources or information flow.

### 3.3 Contract algebra

The algebra operates on the canonicalized UIR form:

| Operator | Meaning |
|---|---|
| `A ∪ B` | Union of entries; budgets sum |
| `A ∩ B` | Intersection of entries; budgets take minimum |
| `A − B` | Set difference; used for capability revocation |
| `A ≤ B` | Subtype: every `may` in A is `may` in B; budgets in A ≤ budgets in B |

---

### 3.4 Effect domain vocabulary and the unknown obligation

Inference normalizes every concrete call chain to a small canonical set of
**domains**; the contract checker then treats those atoms as opaque (it never
interprets a domain's meaning — it only compares and unifies it). The current
canonical domains:

| Domain | Meaning |
|---|---|
| `llm` | call to a language-model provider |
| `db` | database read or write (SQL/ORM) |
| `network` | socket / HTTP client traffic |
| `cache` | cache read or invalidation |
| `io` | interaction with the outside world: stream reads/writes (file, socket, stdio) **and filesystem queries** (stat/readdir/exists — observing external state is an effect even when it mutates nothing) |
| `process` | process lifecycle (spawn, exec, exit, kill) |
| `time` | clock reads and sleeps |
| `email` | mail transport |

Client-side state mutation (`useState` / `useReducer` setters) is a candidate
future domain for the React front end, not one of the current eight.

`pure` is not an effect; it is the **empty row** — a function with no row entry
interacts only with in-process values.

`unknown` is a **tracked obligation, never a silent default**: a call whose
receiver/callee cannot be resolved structurally contributes an `unknown` entry
with modality `unknown`, and the P0.3 acceptance bar is that the corpus reaches
zero such leaves. The mapping from a language/library's concrete surface
(`os.path.exists`, `requests.get`, a `useState` setter) to these domains lives in
DATA lexicons (`racklr/effects/library-tokens.rkt`,
`racklr/effects/imports/library-config.rkt`), injected per front end — the
algebra itself carries no language-specific tokens. Each target emitter reifies
a row's language-neutral atoms back into that language's concrete guard API,
which is what makes the representation reifiable across languages.

## 4. UIR Extensions

### 4.1 New node types

```
(struct uir-effect-row (entries) #:transparent)
(struct uir-effect-entry (name modality ops budget scope) #:transparent)
(struct uir-effect-op (effect op signature) #:transparent)
(struct uir-effect-handler (effect body handlers) #:transparent)
(struct uir-capability (effect scope) #:transparent)
(struct uir-subtype (left right) #:transparent)  ; first-class per working-group answer
```

As built today (`racklr/uir/types.rkt`): `uir-effect-row`, `uir-effect-entry`,
`uir-effect-op`, `uir-effect-handler`, and `uir-effect-decl` exist and are
serialized; `uir-fn` already carries an `effects` slot. `uir-capability` and
`uir-subtype` are Phase 1 proposals, not yet in the schema.

### 4.2 Extended mutator nodes

```
(struct uir-fn   (name params ret body effects decorators) #:transparent)  ; extended
(struct uir-event (name handler effects) #:transparent)                    ; extended
(struct uir-state (name initial setter effects) #:transparent)             ; extended
```

The `effects` field is a `uir-effect-row` or `#f`. The `decorators` field on `uir-fn` is existing; effect annotations may be carried as a decorator.

## 5. Parsing Native Effect Annotations

Effects are written in the host language's native syntax. The parser for each language recognizes that syntax and produces `uir-effect-row` nodes.

### 5.1 Python

Three mechanisms, in priority order:

**Mechanism A: Decorator.** The most natural for FastAPI and Django:

```python
@effects(llm={"max": 5}, db={"reads": "search_index"})
async def summarize(input: str) -> str:
    ...
```

The `lower-python.rkt` parser already handles decorated functions; extending it to recognize `@effects(...)` and extract the row is a direct addition.

**Mechanism B: Type annotation via `Requires`-style brand.** A function can be annotated with a branded type that the parser recognizes:

```python
def summarize(input: str) -> str: ...  # with a __effects__ attribute
summarize.__effects__ = {"llm": {"max": 5}}
```

**Mechanism C: Inference.** If no annotation is present, the effect row is inferred from the body (see §6).

### 5.2 TypeScript / TSX

**Mechanism A: Decorator-like wrapper.** For React components and hooks:

```tsx
const summarize = withEffects({ llm: { max: 5 } })(
  async (input: string) => { ... }
);
```

The `uir-decorated` node already exists; the parser can recognize this pattern and attach the row to the inner `uir-fn`.

**Mechanism B: JSDoc tag.** For code that cannot be structurally modified:

```tsx
/**
 * @effects llm(max=5), db(reads=search_index)
 */
async function summarize(input: string): Promise<string> { ... }
```

The `lower-typescript` front end is extended to recognize `@effects` tags. (TypeScript/TSX parsing and lowering already exist; this is an addition to that front end.)

**Mechanism C: Inference.** Default when no annotation is present.

### 5.3 htmx and Django

htmx-triggered endpoints are ordinary FastAPI or Django view functions; the same Python mechanisms apply. Django form handlers and view functions follow the same pattern. No separate parsing mechanism is needed.

## 6. Effect Inference

The inference pass computes an effect row for every named function and method.
It is **receiver-grounded, never name-grounded**: classification is a property
of the resolved receiver class, resolved class → module → domain, with concrete
library tokens kept in DATA lexicons only (`library-tokens.rkt`,
`imports/library-config.rkt`). There is no `fetch → network` / `db.* → db` table
in engine code.

The pipeline, as built in `racklr/effects/`:

1. **Import resolution (Pass 2.3).** `imports/` reads the raw token stream
   (import statements are flattened away by lowering) and resolves each file's
   `import` / `from … import` into an `import-env`: per-file module path,
   an export graph, and class-qualified effect capabilities derived from
   module paths. No module body is executed.
2. **Receiver-type dataflow.** `receiver-type.rkt` tracks the class of locals
   and `self`/`cls` attributes from constructor assignments (`x = KnownClass(...)`,
   `self.attr = KnownClass(...)`) and aliases, so a later `x.m(...)` resolves
   through the receiver's class. `whole-program.rkt` extends this across files
   and through attribute chains (`self.a.b.m(...)`).
3. **Call-site classification.** Each call is classified in precedence order:
   (a) an intra- or cross-file call-graph edge to a known function/method
   (MRO-resolved `self.m()`, `super().m()`, bare `f()`); (b) a constructor or
   pure builtin/synthetic construct; (c) a receiver-grounded capability via
   the tracked receiver class, a manager attribute (`X.objects.Y`), or an
   imported name; (d) a direct effect root or pure stdlib name from the DATA
   lexicon; (e) otherwise `unknown`.
4. **Whole-program fixpoint.** One monotone fixpoint over the composition of
   every component's call graph, with component-qualified
   `(component . name)` keys, so inheritance that crosses file boundaries
   becomes an edge instead of `unknown`. A function's row is its body evaluated
   through the effect algebra — `sequence` for statements, `choose` for
   branches, `repeatable` for loop bodies/comprehensions/short-circuit
   operands, `weaken-must` for a `try` body — with each call-graph edge
   inserting the callee's current row. Budgets are static invocation upper
   bounds: a direct site contributes 1, a branch takes the per-path maximum, a
   sequence sums, and a loop or a call-graph cycle (widened per
   strongly-connected component) is unbounded (`#f`). Rows converge because the
   effect set is finite, obligations and scopes ascend in a finite-height
   lattice, and cycles are widened.
5. **Typed operations.** A method capability is `domain<Receiver>.verb`
   (e.g. `db<QuerySet>.read`), derived from where the class lives (domain) and
   what the method does (verb, via a per-domain DATA verb table). An
   unclassified verb keeps the coarse `()` ("any op in the domain").
6. **Scope.** Inference claims a scope (`reads=<resource>` /
   `writes=<resource>`, the encoding the runtime guards enforce) only when the
   call chain grounds both the access direction and the resource: a typed op
   set names the receiver class and the verb, and a coarse entry can still be
   grounded when its receiver root is a known class and the called method has a
   single read/write direction in the guard vocabulary. Effects compose their
   scopes through the algebra (`scope-lub`): only an agreed, single resource
   survives; a conflicting or ungrounded resource stays `#f` (uncharacterized,
   never guessed).

**Unknown is a tracked obligation, never a silent default and not a deferral.**
A call that no structural or lexicon rule resolves contributes an `unknown`
entry; the row keeps it through the fixpoint, `type-graph.rkt` reports it, and
the acceptance bar is zero such leaves. The emitter drops `unknown` entries
when materializing concrete rows, because a runtime guard cannot enforce an
unclassified effect — the obligation is to eliminate the leaf, not to ship it.

The inferred rows are written back to `uir-fn.effects`. Hand-written annotations
(§5) win over inference and are never overwritten. Write-back drops `unknown`
entries (a checker signal, not a runtime effect) and materializes an inferred
`must` as `may`: the obligation is an analysis fact about the inferred row,
while a caller-installed effect handler may legitimately interpret or supply
the effect, so the emitted runtime guard treats the inference as a permission
(it keeps the inferred budget, ops and scope). A hand-written row keeps its
declared modality.

### 6.1 Provenance: evidence over assertion

The P0.3 acceptance bar is not "rows exist"; it is **provenance on every
effect edge**: something is `db` because you can point at why, or it is not
classified. An effect entry's provenance is the triple that produced it:

| Provenance | What it names | Where it is recorded |
|---|---|---|
| **Receiver type** | the class whose method was called | the `Receiver` slot of the typed op `db<QuerySet>.read`, resolved by receiver-type dataflow |
| **Call chain** | the caller→callee edge(s) that propagated the entry | the component-qualified `(component . name)` keys and the fixpoint's `edges` table |
| **Tokens** | the source tokens that grounded the classification (module root, method name) | the DATA lexicon rule / import handle that matched |

`type-graph.rkt` already records file-level provenance (`files-by-name`: which
components touch each effect). P4.2 makes provenance **per-edge and
first-class** in the graph substrate (`racklr/graph/provenance.rkt`), so the
same query shape as effervesce's `ask` ("show the exact call chain that makes
this function `db`") is a graph walk rather than a report column.

As built:

- `racklr/effects/provenance.rkt` records one `provenance` value per inference
  run: the **grounds** (the classifying call site, the tokens it grounded on,
  the receiver type receiver-type dataflow resolved, and the classification
  kind `inferred` / `unresolved` / `declared`) and the inferred **call graph**
  (every caller→callee edge with the callee expression the classifier saw).
  `infer-effects` and `infer-effects-all` both take `#:provenance-record`, a box
  filled with that value. `infer-effects` keeps its legacy
  `#:provenance-table` view (the rendered `name: chain` strings Effervesce's
  bridge checker reports) alongside the structured record. A blessed capability from the DATA config is grounded
  at the method definition (`declared`), with the module path, class, and
  method as its tokens.
- The projection emits every row entry as a `fn-effect` edge, every ground as a
  `grounds` edge to its stable-origin site (with `site-expression`,
  `site-token`, `site-receiver`, `site-kind`, `site-effect`, `site-coverage`,
  `site-file`, `site-chain`, and `site-line` when known atoms), and every
  call-graph edge as a `call-site` edge carrying the classifier's callee
  expression and the call site's origin. A **provenance path** is a walk from a function along `call-site`
  edges to a `grounds` edge; `provenance-paths` returns the exact
  caller→callee chain (shortest per ground) for a given function/effect edge.
- "No effect edge exists without provenance" is enforced at projection time by
  the same atom-level reachability traversal the query uses: the graph builder
  raises if any effect edge cannot reach a ground. `provenance-missing` checks
  the same property from the row/provenance tables without enumerating paths,
  and the test suite cross-checks that the record-level and atom-level answers
  agree (including a deliberately dropped call-site link, which only the
  atom-level check detects). `tools/provenance-corpus.rkt` runs the check over
  the Django corpus without touching the baseline and prints the counts, the
  distinct-origin count, and a sha256 fingerprint of the sorted origin ids
  (repo-relative components, so the fingerprint is location-independent;
  `--origins` dumps the ids so two runs diff directly).
- The atom vocabulary, the reusable parsed index, and the completeness check are
  separate modules (`racklr/graph/provenance-atoms.rkt`,
  `racklr/graph/provenance-index.rkt`, `racklr/graph/provenance-check.rkt`),
  re-exported from `racklr/graph/provenance.rkt` so consumers see one API.
- **Stable origins (nc-4A19).** Every ground and call hop carries a
  `prov-origin` (`racklr/effects/origin.rkt`): the **file** component, the
  enclosing **owner** function, the structural **receiver chain** (the dotted
  source names taken from the UIR callee, never parsed back out of a rendered
  expression), and a source-structural **positional discriminator** (the
  ordinal of the call node in the owner body's pre-order walk) standing in for
  a line number while UIR carries no source positions; the origin keeps a
  `line` field that joins the identity once the front ends record positions.
  The identity deliberately excludes the effect, the kind, the coverage, the
  tokens, and the resolved receiver class: those are inference results, and
  keying identity on them is value-dependent, which partitions one site's
  evidence and makes graph drift across runs undiagnosable. The projection
  names `site` atoms by the origin id (`file::owner@position:chain`), so the
  readable call expression is a `site-expression` display atom and a rendering
  change cannot re-key the graph; `site-file`, `site-line` (when known), and
  `site-chain` atoms expose the origin components. `provenance-origins`
  returns the sorted origin ids — two runs over the same source agree, and a
  diff localises drift to the sites that moved. Two identical expressions at
  different positions are distinct origins (previously they collapsed into one
  ground).

### 6.2 Confidence, coverage, and transitive profiles

Provenance says *why* an effect edge exists. Two labels say *how strongly* and
*how generally* the claim is made, and every function exposes the transitive
closure of its effects with those labels. The model is Rainbow's: every result
carries a label set by its weakest link, and every theorem exposes a transitive
axiom profile.

**Confidence** — how the edge was established (strongest first):

| Label | Evidence |
|---|---|
| `inferred` | a classifying call site or call-graph edge inference observed |
| `declared` | a capability asserted by the DATA config at a method definition |
| `unknown` | the tracked elimination obligation (classification kind `unresolved`) |

**Coverage** — how far the claim generalizes (strongest first):

| Label | Evidence |
|---|---|
| `universal` | for-all structural evidence: a call-graph edge, literal/library call site, declared capability, self/MRO dispatch, or imported handle |
| `census-param` | a worked instance: the receiver type came from parameter dataflow (the census's `param` receiver shape), so the claim holds for the actual call arguments |
| `local-literal` | a worked instance: the receiver type came from a tracked local / self-attribute / call-result value in the body |

Labels combine with the **weakest link** (`racklr/effects/labels.rkt`): a profile
that reaches one unknown or one worked-instance-only edge cannot claim a
stronger label as a whole. Both label orders and the combining functions are
exported and unit-tested.

As built:

- Every ground records its coverage (`prov-site` gains a coverage field and the
  projection adds a `site-coverage` atom per site). `infer-effects` labels
  structural grounds `universal` and unresolved sites `local-literal`;
  `infer-effects-all` distinguishes a parameter-rooted site (`census-param`)
  from a tracked local/attribute/chain/call-result site (`local-literal`) using
  the classifier's evidence side channel (`classify-call-all` reports whether
  the classification needed receiver-type dataflow or was a structural rule;
  the classification result is unchanged). The classification kind maps to the
  confidence label; no separate flag is stored.
- `racklr/graph/profile.rkt` answers `transitive-profile`: a breadth-first walk
  from a function along the call-site edges, one shortest witness chain per
  ground, then per effect the weakest-link confidence and coverage with those
  witnesses. `transitive-profiles` returns every function's profile.
- The eliminate-unknown obligation is data: `effect-profile-obligations` lists
  every unresolved ground reachable from the function, with its chain and
  coverage evidence kind, and `effect-profile-complete?` is
  `(null? obligations)`. A consumer can report or drive down each obligation
  without re-deriving the call graph.
- `tools/provenance-corpus.rkt` reports the ground-site coverage histogram,
  and `--profiles` adds the transitive-profile report: complete vs incomplete
  functions, profile entries by effect and by confidence/coverage, and the open
  obligation count, over a real corpus.
- `racklr-test/effect-profile-test.rkt` covers the label orders, the
  weakest-link combination, the kind→confidence map, coverage derivation for
  structural / parameter / local evidence in both inference drivers, declared
  grounds, transitive witnesses, mixed-confidence aggregation, and the
  unknown-obligation data structure.

## 7. Contract Algebra Pass

Per the working-group's answers:

- **(10.3) First-class:** The `≤` relation is a `uir-subtype` node that survives lowering.
- **(10.5) Static first, runtime fallback:** The pass attempts static resolution of budgets and scopes. When it can prove a constraint, it emits a compile-time check. When it cannot, it emits a runtime guard.
- **(10.4) Jolt:** The shared validator is built in Jolt, called via C ABI.
- **(10.6) Fixture:** A shared fixture spec exercises all five structural features.

The pass checks three properties:

**Subtyping.** A mutator's inferred or annotated row must be a subtype of its component's allowed row. If a component declares `<may state-mutation>` and a mutator is inferred to use `<may network>`, the pass reports a compile-time error unless the component's row is widened.

**Budgets.** A mutator annotated `<may llm(max=5)>` must not statically call the LLM more than five times on any execution path. If the count is not statically resolvable, the pass emits a runtime guard.

**Prohibitions.** A mutator annotated `<must_not db>` must not call any function inferred to have the `db` effect.

Errors are reported in the same diagnostic channel as parse and lowering errors.

## 8. Runtime Enforcement via Jolt

For effects that cannot be statically resolved, the pass emits a runtime guard that calls the Jolt validator. The validator's interface:

```c
int validate_effects(const char* agent_type, const char* effects_json, char** error_msg);
```

### 8.1 Python emission (FastAPI / Django)

For a FastAPI route handler:

```python
@app.post("/profile")
@effects(db={"writes": "user"}, cache={"revalidates": "/profile"})
async def update_profile(data: ProfileData):
    __validate_effects("profile-mutator", ["db:writes=user", "cache:revalidates=/profile"])
    await db.user.update(where={"id": data.id}, data=data)
    revalidate_path("/profile")
```

The `__validate_effects` function is a thin wrapper that loads the Jolt shared library via `ctypes` or `cffi`. For Django views, the same wrapper is emitted inside the view function.

### 8.2 TypeScript / React emission

For a React event handler:

```tsx
<button onClick={__withEffects("counter-mutator", ["state-mutation:component=counter"], () => setCount(count + 1))}>
  Click
</button>
```

The `__withEffects` wrapper performs the same validation before invoking the handler. For htmx-triggered endpoints, the server-side Python guard applies.

### 8.3 Validator deployment

The Jolt validator is compiled once to a shared library (`.so`/`.dylib`/`.dll`) and called from:

- **Python:** `ctypes` / `cffi`
- **TypeScript/Node.js:** `ffi-napi` / `koffi`
- **Rust:** `extern "C"` link
- **Clojure/Jolt:** direct call

The same binary enforces the same contract everywhere.

## 9. Revised Pipeline

**As built (Phase 0 — the P0.3 path):**

```
Pass 1:    Parse (per-language ANTLR grammar)
Pass 2:    CST → UIR (lowering; existing)
Pass 2.3:  Import resolution (token-level import extraction → module table →
           export fixpoint → import-env; no module body executes)
Pass 2.4:  Effect inference (receiver-type dataflow + one whole-program
           monotone fixpoint, class → module → domain, typed ops; §6)
Pass 2.5:  Provenance + graph projection (type-graph.rkt: fn-effects,
           fn-effect-row, effect-entry, effect-op, inherits atoms)
Pass 3:    Target lowering + emission (existing)
```

**Planned (later phases, not on the P0.3 path):**

```
Pass 1.5:  Effect annotation extraction (parser → uir-effect-row)   — Phase 2
Pass 4:    Contract algebra (subtyping, budgets, prohibitions)       — Phase 1
Pass 5:    Runtime fallback emission (Jolt validator calls)          — Phase 5
```

Passes 2.3–2.5 are language-agnostic; only the grammar and the DATA lexicon
(`library-tokens.rkt`, `imports/library-config.rkt`) are per-language.

## 11. Phased Implementation Plan

Phase numbers here map onto ROADMAP.md; the P0.3 bar is the Phase 0 entry.

**Phase 0 — inference to the acceptance bar (in progress).**
Import resolution, receiver-type dataflow, and the whole-program fixpoint are
built and green (§6). Remaining: drive the Django corpus to zero `unknown`
leaves and make provenance per-edge and first-class (§6.1).

**Phase 1 — effect algebra (rows, fixpoint, subtyping built; polymorphism planned).**
`racklr/effects/algebra/` is a standalone library: effect rows as sets of
(effect, provenance) pairs, join / sequence / choose / scope over them, a
generic monotone fixpoint driver that `infer.rkt` and `whole-program.rkt` now
run the inference fixpoint on, and row subtyping with handler interpretation
(the bridge checker's capability table generalized to rows). Property tests in
`racklr-test/effects-algebra-property-test.rkt` cover the algebra laws, fixpoint
monotonicity, and the subtyping laws. Remaining for the phase: effect
polymorphism (row holes) and the Pass-4 contract check over the new relation.

## 12. Fixture Specification

The fixture exercises all five structural features. It is written in each target language's native syntax and must round-trip through the UIR.

**Python (FastAPI) source:**

```python
from myapp.effects import effects, llm, db, network

@effects(llm={"max": 5})
async def summarize(input: str) -> str:
    return await llm.query(f"Summarize: {input}")

@effects(llm={"max": 10}, db={"reads": "search_index"})
async def researcher(query: str) -> Report:
    rows = await db.fetch("search_index", query)
    return await llm.query(f"Analyze: {rows}")

@effects(must_not={"network"})
def forbidden(x: str) -> str:
    return x

@effects(llm={"max": 15}, db={"reads": "search_index"})
async def pipeline(seed: str) -> Report:
    report = await researcher(seed)
    summary = await summarize(report.summary)
    return Report(report.rows, summary)
```

**Expected UIR (abridged):**

```
(uir-fn "pipeline"
  ...
  (uir-effect-row
    (list (uir-effect-entry "llm" "may" '() 15 #f)
          (uir-effect-entry "db"  "may" '() #f "reads=search_index"))))
```

The fixture is emitted to all target languages. Each target's test verifies:

1. Budget enforcement (call count exceeds `max` → violation).
2. Prohibition enforcement (`must_not` effect invoked → violation).
3. Obligation enforcement (`must` effect not invoked → violation).
4. Scope enforcement (`db(reads=search_index)` invoked on wrong table → violation).
5. Subtyping (`summarize` callable where `researcher` is expected, but not vice versa).

## 13. Open Questions

1. **JSDoc vs. wrapper for TypeScript.** JSDoc is less invasive but not checked by TypeScript. `withEffects(...)` changes the function signature. Should the parser support both?
2. **Django middleware vs. view decorators.** Should effects be extracted from view decorators only, or also from middleware that wraps handlers?
3. **Client-side state mutation granularity.** Should `state-mutation` be tracked at the component level, the hook level, or the setter level?
4. **Runtime guard overhead.** `__withEffects` adds a function call per event invocation. Should the emitter support a sampled validation mode for high-frequency events?
5. **Cross-language consistency.** The Jolt validator is the single source of truth for runtime enforcement, but static inference in racklr and runtime tracking in the target language's effect library may diverge. How is this divergence detected?
